# 两轴因子产出 prompt（v1 · 2026-09-15）

> 用途：**两轴因子产出**。取一段已结算腿，按「方向轴 / 波动轴」两条线并行跑若干 worker，
> 各产出一批候选因子，再交给 `factor_induction` 归纳 + 去重。
>
> ⚠️ **首轮挖掘与周期性挖掘共用这一套 prompt、同一份输出 schema、同一套判据。**
> 两者只差三件事：`MODE`、样本窗口大小、（周期模式多给一段）现有因子库摘要。见 §5。
>
> 与既有链路的关系：
> - 本 prompt 产出的是**候选因子库**（`candidates_<axis>_<worker>.json`），不是直接写库。
> - 归纳去重后若要把幸存因子落进某只狗，再映射成 `src/reflect_apply.py` 认的
>   `{alpha_factors, factor_types, factor_desc, key_slugs}` 即可（见 §7）。
> - 两轴的定义与实测证据见 [`../beidan_axis_two_stage.md`](../beidan_axis_two_stage.md)。

## 0. 一页速览

| 项 | 首轮（initial） | 周期（periodic） |
|---|---|
| 触发 | 手动跑一次 | 每 N 天 / 每日增量 |
| 窗口 | 最开始的 15 个可回放天（`06-28 … 07-21`） | 滚动窗口，建议 **3~5 天** |
| 样本 | 234 场｜**311 腿**（219 条 `gl=0` 干净腿 + 92 条让球对照；其中过门 120 条） | 1 天 65 腿 / 3 天 194 / 5 天 322 / 7 天 443（全池均值） |
| 输入尺寸 | 6 份 × **≈24k 字符 ≈ 11.5k tokens** | 1 天 ≈15k 字符 ≈ 7.2k；5 天 ≈72k ≈ 34.6k（按腿数切） |
| 切批规则 | **每 worker ≤120 腿（≈27k 字符 ≈ 13k tokens）**，按腿数切、不按天数切 | 同 |
| 成本 | 6 次 ≈ 60k 输入 tokens ≈ **0.05~0.25 元** | 每天 ≈0.05 元 |
| 产出 | 每 worker 8~15 条候选 → 合并 60~90 条 | 每轮 5~15 条增量 |
| 下游 | `python3 -m src.factor_induction --roles <狗>`（判重：slugs 对称差 ≤2 且名字相似 ≥0.60） | 同 |

⚠️ **功效提醒**：首轮 15 天 / 311 腿，按轴切一刀后每个条件的 CI 约 ±5~8pp。
挖掘的目标是**建/更新候选条件库**，不是证明显著性 —— 显著性留给 walk-forward。

## 1. 输入数据契约

### 1.1 一行一腿（每行 = 一个「场次 × 侧」的赛前快照 + 赛后标签）

```
<day> <lota短号> <side> mp=<市场p̂> od=<北单赔率> span=<三侧分散度> x=<mp×od> gl=<让球线> src=<P|H>
  | ah=<h0>/<line0>/<a0>→<h1>/<line1>/<a1>
  | eu=<欧赔首h/d/a>→<末h/d/a>
  | disp=<离散末h/d/a> ds=<离散首h/d/a>
  | gap=<实力差> gs=<预期进球和>
  | sp=<开奖SP> hit=<0/1> z=<SP·1{中}> d=<1{中}−mp>
```

真实样例（`scripts/factor_mine_input.py` 的产物，可整段贴给 LLM）：

```
06-28 4469357 A mp=0.48 od=2.51 span=0.51 x=1.21 gl=-1 src=H | ah=0.86/0.50/1.02->1.00/0.50/0.87 | eu=1.80/3.35/3.10->+0.01/-0.08/-0.25 | disp=7.0/10.8/17.1 ds=5.9/12.9/11.2 | gap=1.15 gs=2.93 | sp=4.10 hit=0 z=0.00 d=-0.48
06-28 4469360 A mp=0.35 od=4.93 span=0.87 x=1.72 gl=-1 src=H | ah=na/na/na->na/na/na | eu=1.37/4.25/4.80->-0.10/-0.01/-0.08 | disp=2.2/5.6/28.8 ds=2.0/3.7/28.9 | gap=1.43 gs=2.84 | sp=5.23 hit=1 z=5.23 d=+0.65
```

实测尺寸：**225 字符/腿**（含 ah 首末 6 数、eu 三侧变动、disp 首末、gap/gs、gl/src）。
首轮 15 天 = 311 腿 → 3 组 ×（98~107 腿）→ 每份 ≈24k 字符 ≈11.5k tokens。
滚动窗口均值：1 天 65 腿 / 3 天 194 腿 / 5 天 322 腿 / 7 天 443 腿。

字段口径：

| 字段 | 含义 | 备注 |
|---|---|---|
| `mp` | 锐市场（Pinnacle 1X2 → 该让球线）去水概率 | **这是方向轴的基准** |
| `od` | 北单赛前赔率（该侧） | |
| `span` | 三侧北单赔率 `(max−min)/mean` | **波动轴的排序键**，越小＝结构越集中 |
| `x` | `mp × od`；>1 = 奖池比锐市场便宜 | 引擎的价格门，**不是方向信号** |
| `gl` / `src` | 让球线 / 市场源（`P`=Pinnacle，`H`=让球欧盘换算） | 见 §2 硬约束 8 |
| `ah` | 皇冠亚盘 首→末（主水位/让球线/客水位） | `dline≠0` = 升/退盘 |
| `eu` | Pinnacle 欧赔 首→末（h/d/a） | |
| `disp` / `ds` | 离散指数 末行 / 首行 | |
| `gap` / `gs` | 公平盘 主客实力差 / 预期进球和 | |
| `sp` / `hit` / `z` / `d` | 开奖SP / 是否命中 / `SP·1{中}` / `1{中}−mp` | **只有这四个是赛后字段，禁止写进条件** |

### 1.2 基线段（必须给，否则 LLM 会把「今天整体便宜」当成「这场有边际」）

## 2. SYSTEM prompt（整段可复制；`{{...}}` 为注入位）

```text
你是北单串关的因子挖掘器。你看的是**已结算的历史腿**，任务是产出一批
「赛前可观测、能解释某一侧为什么被奖池错价」的候选因子。你不下单、不选票、不负责任何资金决策。

## 本轮只挖一个轴

{{AXIS_BLOCK}}

## 本轮是哪种挖掘

{{MODE_BLOCK}}

## 判据口径（唯一标准，别自创）

腿的收益标签是 `z = 开奖SP × 1{中}`，`y = E[z]`；4 关票的**每腿打平线 = 1.11371**
（`(1/0.65)^(1/4)`，0.65 只在整票收一次）。但**两轴必须分开归因**：

- 方向轴判据：`d = 1{中} − mp`（命中率相对锐市场 p̂ 的边际，单位 pp）
- 波动轴判据：`ā = 开奖SP / 赛前赔率`（赔率保不保得住）与 `span`（三侧结构分散度）
- `y` 是两轴的乘积结果，**只能用来看一眼，不能拿来挑因子**。

样本里给你 `d`（定方向）与 `z`/`sp`（看收益），但它们只是**标签**：
写因子条件时一个都不许用。

## 硬约束（违反即作废）

1. ⛔ **禁止用 x、赔率高低、SP 大小作为方向因子的条件**。那是波动轴的东西：
   实测「x 越大 ā 越差」（x≤1 → 0.95；门内 → 0.78；结构最分散档 → 0.61），
   按 x 排序选腿的方向边际是 −9 ~ −13pp。凡是形如「x 高」「高赔」「高 SP」的条件，
   一律归到波动轴，不许写成方向因子。
2. ⛔ **禁止把赛后信息写进条件**：`sp / hit / z / 比分 / 开奖码 / 「这场爆冷了」`
   只能出现在 __证据__ 里，不能出现在条件里。
3. ⛔ **禁止只看命中样本**。同一条件必须在「中」和「不中」两侧都有样本，
   并且要报出两边的计数。只说中的那几条 = 没有区分度。
4. ⛔ **禁止输出同义反复**：如「冷门侧容易爆冷」「强队容易赢」。
   条件必须是可判定字段（mp / span / ah / eu / disp / gap / gs 及其首末差）。
5. ✅ **每条因子必须能回答三件事**：条件是什么（可判定）、作用在哪个轴、期望符号是正还是负。
6. ✅ 样本数 <20 的条件必须标 `"low_sample": true`，别包装成发现。
7. ✅ 命名规范（为了后面自动去重）：**4~10 个汉字**，不含数字/空格/emoji/括号，
   结构 = 「可观测特征 + 作用方向」，例如 `冷门侧盘口不动`、`三侧赔率收敛`。
   同一含义只允许一种写法（不要写「高赔冷门」「冷门高赔」「冷门方高水」三种）。
8. ⛔ `src=H`（让球欧盘换算）的腿只能当**对照组**：它们的市场 p̂ 是换算产物，
   已被证实不是真错价。因子条件**不许只在 `src=H` 的样本上成立**。
9. ⛔ **禁止把「宇宙定义」写成条件**：`gl == 0`、`src == P`、`x >= 1.11` 都不是因子
   —— 它们对语料里的腿恒成立，没有筛选力。
10. ⛔ **方向轴禁止裸单侧条件**：只写 `side_is == H` 等于「买主队」。条件里必须至少有一个
   **结构字段**（mp/ah/eu/disp/gap/gs）与侧绑定。
11. ⛔ **样本地板**：`evidence.n < 8`，或 `hit_n < 2`，或 `miss_n < 2`，或对照组
   `counter` 的 n < 5 —— 一律写进 `rejected`。
12. ⛔ **`cond` 必须能被引擎求值**：只能用 §6.2 的语法。写不出合法 `cond` 的因子
   放进 `rejected`，不许在 `factors` 里写「无法求值」「需另计算」。
13. ⛔ **方向轴的 `side` 必须可解析**：`H`/`D`/`A`，或 `最低mp侧`/`最高赔侧`/`gap正号侧`/`该侧`；
   方向轴不许「不指定」。
14. ⛔ **方向因子必须能推出「每场唯一一侧」**：用 `rank_mp == 1`、`rank_od == 3` 这类
   **名次条件**，或 `gap` 的正负号侧。全局字段（span/gs/gl/x）配 `该侧` **不算选侧规则** ——
   这类条件三侧同时成立，样本被稀释，也落不到票上。
15. ✅ `ah.water` / `eu.move` / `disp` 是「我方」字段；`D` 侧无亚盘水位，
   用 `ah.water` 的条件自动只覆盖 H/A，属正常写法。

16. ⛔ **单位统一**：`d_pp` 一律写百分点（`+6.8`，不是 `0.068`）。
17. ✅ `rank_*`（`rank_mp` / `rank_od` / `rank_disp`）由引擎按**该场三侧全量**算（1 = 最低），
    直接写 `rank_mp == 1`，不要自己绕三侧比较。
18. ✅ 首末要显式选一个：`ah.line` = 末行、`ah.line0` = 首行；水位 `ah.h1/a1`（末）与 `ah.h0/a0`（首）。

⚠️ **引擎侧硬性要求（2026-09-15 复核实测）**：`cond` 求值必须在**该场三侧全量**上做，
不能用"只过了 x≥1 门槛的那几条腿"当宇宙 —— 否则 `rank_*` 与 `disp >= disp.h` 这类
比较字段会退化（单侧入池的比赛里那一侧天然 rank=1）。首轮 7 天复核里 7 条"偏离"全部来自这一点。

## 已证伪清单（别再挖，挖了也会被剔除）

- 「离散凝聚」（单关狗旗舰策略）：在北单门内 `d` 只有 +0.1pp，无效。
- 「升盘」「主队水位走高」「欧赔上升且最凝聚」：`d` 为负（−0.3 ~ −2.5pp）。
- 「热门侧」：`d = −0.3pp`，但 `ā = 1.01`（赔率保得住）——属波动轴，别写成方向因子。
- 「x > 1.5385 的腿」：已证实是让球欧盘换算产物，不是真错价。

### 2.1 `{{AXIS_BLOCK}}` — 方向轴（`AXIS=directional`）

```text
### 轴 = 方向轴（directional）

你要回答的是：**什么赛前条件能让某一侧的命中率高于锐市场给的 p̂（d > 0）**。

可用信号（都是赛前可观测）：
- 市场结构：该侧 mp 的高低、三侧 mp 的排序、mp 是否被池子反向定价；
- 亚盘：水位（h1/a1）高低、让球线首→末变化、盘口是否不动；
- 离散：末行三侧分布、我方是否最发散 / 最凝聚、离散首→末变化；
- 欧赔：我方赔率首→末相对变化；
- 公平盘：实力差、预期进球和。

已知的粗先验（可用作起点，但必须自己在样本里核数）：
冷门侧 +5.2pp｜最发散侧 +4.9｜主队水位走低 +4.9｜弱侧(mp<0.35) +3.7｜
小球(<2.6) +3.8｜欧赔下沉 +3.1｜盘口不动 +0.8｜最凝聚侧 +0.1｜热门侧 −0.3

输出要求：`side` 必须写清「买哪一侧」（或写明判定规则），`expect` 用 `+` / `-`。
目标不是罗列条件，而是找到**能把 d 抬起来的组合**（单条 +2pp 以上才有意义）。
```

### 2.2 `{{AXIS_BLOCK}}` — 波动轴（`AXIS=volatility`）

```text
### 轴 = 波动轴（volatility）

你要回答的是：**什么赛前条件能让赛前赔率更可能被兑现（ā 高），或者让收益尾部更厚**。
这一轴**不许**声称命中率提升 —— 命中率是方向轴的事。

可用信号：
- 结构集中度：`span`（三侧北单赔率分散度，越小越集中）、三侧赔率是否有明显冷门；
- 该侧赔率绝对高度（高赔 = 池子会砍得更狠）：实测冷门侧 ā=0.64、热门侧 ā=1.01；
- 亚盘水位与让球线的稳定性（走水快 = 临场变盘 = SP 缩水风险）；
- 离散首→末变化（分歧收敛 vs 扩大）；
- 欧赔首→末变化（价格已经动过的腿，开奖时更可能再动）。

已知的粗先验：span 三档 ā = 0.98 / 0.80 / 0.61（T1/T2/T3）；
按 x 降序取腿 ā=0.65（最差），x≤1 的腿 ā=0.95。

输出要求：`expect` 说明它对排序的影响（`+` = 应当排前，`-` = 应当排后）。
`side` 通常写「不指定」。因子要能直接回答：**这条腿的赔率值不值得连乘**。
```

### 2.3 `{{MODE_BLOCK}}` — 首轮 / 周期（同一套 prompt 的唯一模式差异）

```text
### mode = initial（首轮）

你面对的是一个**空因子库**。目标是尽可能把候选条件铺开：
- 8~15 条，允许写到只是"看起来像"的条件（样本 n≥20 即可），每条必须带
  `hypothesis` 一句话说明它为什么可能成立（机制），供后续归纳时判断是否同源；
- 不要为了凑数把同一个条件写成多条（如「冷门侧低水」和「低水冷门侧」）。
```

```text
### mode = periodic（周期）

你面对的是**已有因子库**（见【现有因子库】段）。目标是**增量与修订**，不是重铺一遍：
- 只输出两类因子：① 库里没有的新条件；② 对库内已有因子的**修订**（阈值改、方向反、
  条件收窄）。修订用同一个 `name`，并在 `revise_of` 里写明要改哪条、改成什么；
- 已被库内因子覆盖的，不要再写一遍；样本不足或已被证伪的，写进 `rejected`；
- 3~8 条即可。库里某条因子在本窗口明显失效（如 n≥25 且 d 反号），写进 `rejected`
  并标 `"suggest_retire": "因子名"`，由退役流处理，你不要自己删。
```

{{EXISTING_FACTORS}}

【要求（周期模式追加）】
5. 逐条判断库内因子在本窗口是否仍成立：仍成立→不要输出；明显反号且 n≥25→写进 rejected
   并标 suggest_retire；需要改阈值/收窄→用同名因子 + revise_of 输出修订。
```

`{{EXISTING_FACTORS}}` 由引擎从 `factor_memory.json` 生成一行一条
（`名字｜directional|volatility｜desc 前 40 字`），周期窗口 3~5 天时约 30~60 行、≈1.5k 字符。

## 5. 编排：两种触发，同一套 prompt

```text
                    ┌─ 首轮 initial：手动，窗口 = 前 15 天
同一个 miner(axis, window, mode, existing_factors)
                    └─ 周期 periodic：每 N 天，窗口 = 最近 3~5 天
                              │
                              ├─ worker ≤120 腿/次（按腿数切批，不按天数）
                              ├─ 2 轴 × ceil(腿数/120) 个 worker（互不依赖，可并发）
                              ▼
                        factors[]（统一 JSON）
                              ▼
        factor_induction 归纳 + 去重 → factor_memory / fac_*.json
                              ▼
        （周期）退役流按 suggest_retire / 触发率处理失效因子
```

两种触发的差异（**只有这些**）：

| 维度 | initial | periodic |
|---|---|---|
| `MODE_BLOCK` | 空库，铺开 8~15 条 | 带库，增量/修订 3~8 条 |
| 窗口 | 前 15 天（311 腿） | 最近 3~5 天（194~322 腿） |
| 额外输入 | — | `{{EXISTING_FACTORS}}` |
| 输出 schema | **完全相同** | **完全相同** |
| 判据口径 | **完全相同**（d / ā / span） | **完全相同** |

- 并行：首轮 = 2 轴 × 3 组 = 6 次；周期 = 2 轴 × 1~3 次。worker 之间无共享状态。
- 同一窗口被两条轴各跑一遍，**不是重复劳动**：方向轴要的是 `d` 的两端，波动轴要的是 `ā`
  的两端，同一条件在两条轴上的结论经常相反（如「热门侧」d=−0.3pp 但 ā=1.01）。
- 归并顺序建议：有 `evidence` 的优先 → `n` 大的优先 → `low_sample=true` 降级。

## 6. 与「归纳 + 去重」的接法

`src/factor_induction.py` 的判重是确定性的两两比较：

```text
同一条因子  ⟺  slugs 对称差 ≤ 2  且  名字相似度 ≥ 0.60（PER_FACTOR_PAIR_CAP=3）
```

所以本 prompt 的产出必须满足：

1. **命名规范统一**（§2 硬约束 7）：同一个含义只用一种写法，否则判重失效。
2. **slugs 只报真正依赖的段**（从白名单选）：slugs 差集 >2 就不会被判成同一族，
   而漏报 slugs 又会让分析时加载不到数据段。
3. 归纳阶段**不要拿 `y` 做筛选**，只用 `d_pp`（方向轴）与 `ā`（波动轴）做排序，
   显著性留给 walk-forward。

### 6.1 让两套真正合一的唯一前提：归因改由引擎算

现在周期路径（`src/agent.py::run_reflect` → `src/reflect_apply.py`）里，
每场命中哪些因子是**LLM 报的** `factor_attribution: {"order_N": [...]}`。
首轮挖掘没有票、没有 order，这条路走不通 —— 两套要合一，就得把这个字段去掉：

```text
LLM 只产出 factors[]（含机器可读 cond）
        │
引擎用 cond 在该窗口所有已结算腿上求值 → 哪些腿满足条件（= 归因，确定性、可复算）
        │
factor_memory.record(name, hit, profit, type=..., sp=..., date=...)
        │
save_factor(Factor(id=fac_<name>, slugs=..., content=desc))
```

- 好处：归因、hit/profit、触发率全部由引擎算，首轮与周期同一套；LLM 无法通过
  乱报归因把因子统计做成"好看"。
- 代价：`cond` 必须是**可求值的小语法**（见 §6.2），否则退化回人肉归属。
- 过渡做法：引擎暂不支持 `cond` 时，把它原样并进 `factor_desc` 末尾
  （`『条件: ...』`），先跑通挖掘 → 归纳，再补求值器。

### 6.2 `cond` 小语法（唯一来源：`src/axis_miner.py` 的 SYSTEM 模板）

```
cond   := or_expr
or_expr:= and_expr (" 或 " and_expr)*
and_expr:= term (" 且 " term)*
term   := field op value
op     := == | != | < | <= | > | >=
```

| 类别 | 字段 |
|---|---|
| 选侧 | `self` / `side_is` / `rank_mp` / `rank_od`（名次 1 = 最低 mp / 最低赔率） |
| 我方 | `mp` / `od` / `ah.water` / `ah.line` / `ah.dline` / `eu.move` / `disp` / `disp.ds` |
| 全局 | `span` / `gl` / `x` / `gap` / `gs` / `ah.h0|h1|a0|a1|line0|line1` / `eu.h|d|a` / `disp.h|d|a` / `disp.ds.h|d|a` |

例：`rank_mp == 1 且 ah.dline == 0`、`mp <= 0.40 且 eu.move <= -0.05`、
`ah.water <= 0.91`、`span <= 0.49`、`gs < 2.6`、`side_is == H 或 side_is == A`。

⚠️ 三个实测踩过的坑（已写进硬约束 9/12/14）：
`gl == 0` 这类"宇宙定义"不是因子；写不出合法 cond 的必须进 `rejected`；
**全局字段 + `该侧` 不构成选侧规则**（三侧同时成立），方向因子必须用名次条件或 `gap` 符号侧。

## 7. 落库（幸存因子 → 某只狗）

归纳去重后，**首选**走 §6.1 的引擎归因路径：引擎按 `cond` 在窗口腿上求值 → 写
`factor_memory`（含 type / desc / hit / profit / sp）→ `save_factor(fac_<name>.json)`。
这条路首轮与周期完全一致，不依赖任何"有没有下单"。

过渡期如果要沿用现有 `reflect_apply`（它要求 LLM 报 `factor_attribution`），映射如下：

```json
{
  "alpha_factors": ["冷门侧盘口不动", "三侧赔率收敛"],
  "factor_types": {"冷门侧盘口不动": "directional", "三侧赔率收敛": "volatility"},
  "factor_desc": {
    "冷门侧盘口不动": "当该侧 mp 为三侧最低且亚盘让球线首末不变时，方向边际 +6.8pp（n=46）",
    "三侧赔率收敛": "三侧北单赔率 span≤0.49 时，开奖 SP 保留率中位 0.98（全样本 0.90），排序靠前"
  },
  "key_slugs": ["asian-handicap-pinnacle", "discrete-odds"],
  "noise_slugs": ["match-head"],
  "reflection": "…"
}
```

注意：`factor_types` 缺一条就会被 `reflect_apply` 整批拒绝写入（防高 SP 防冷因子被静默
默认成 directional），所以两轴产物必须分别标注、不可混用。
